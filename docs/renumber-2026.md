## 3. 对 railcn 的影响面（webapp/data/rail.db 实测，2026-11-03）

| 表 | 行数 | 绑定点 | 风险 |
| --- | --- | --- | --- |
| trains | 457,839 | code+date（2026-07-04 → 2026-11-17） | 历史按日期留存没问题；新旧号将按日期自然共存 |
| route_day / route_tpl | 316,587 / 13,427 | train_no+date / train_no+fp | **train_no 内部码同步变**，配对只能靠停站指纹 |
| train_override | 54 | code（硬规则 4：校正绑车次号） | 改号后匹配不上＝人工校正「失踪」 |
| curate | 12,779 | code+date | 历史行不动，查询层串号即可 |
| day_skip | 65,685 | date+code | 低 |

字头分布（近 30 天去重车次）：G 6518 / D 3797 / C 3744 / K 1593 / S 1075 / Z 302 / T 197 / Y 185，纯数字普速约 400。
阶段一（11-25）打到 Z/T/K/Y/纯数字普速约 2500 个车次；阶段二打到 G/D/C/S 全部。

### 三个深层风险

1. **号段语义漂移**：新 T/K/D 与旧 T/K/D 含义完全不同（旧 T=特快普速，新 T=300 动车组）。历史库的
   「K666」（旧快速普速）与 2027 年的「K666」（新动车组）是两趟车。**任何按字头推断车种/速度的逻辑都会错**；
   train_override 不能按字符串裸挂到新号，必须经确认的对照关系迁移，且防号段复用。
2. **train_no 连续性失效**：route_tpl 按 train_no 键。配对必须用「停站指纹 fp / 起讫站+各站时刻」，
   不能指望 train_no 或 code 连续。
3. **窗口期很短**：12306 预售期规则让新车次提前 15 天可见——**11-10 起新旧号同屏**，是自动建对照表的
   最佳（唯一轻松）窗口；错过就要等切换后做全量 diff。

## 4. 准备方案（2026-11-03 定案：不做配对，改号后全部车次重新校对）

用户决定：**不做新旧车次对照表、不做自动配对、不做校正迁移**——改号后所有车次重新走一遍人工校对；
旧校正**直接清掉**（不归档），**老车次不进待校对**。数据面天然安全：trains / route_day / curate 都是
(code, date) 键，新旧号按日期自然共存，历史查询不受影响。

### 4.1 旧校正：直接清掉

- 阶段一（11-25）：清全部旧校正（只清 `updated_at < 切换日` 的，切换日后新校的不动）。
- 阶段二：只清 G/D/C/S 字头（阶段一之后新校的 V/N/Z/Y 等保留）。

### 4.2 待校对只认新车次（已实现，2026-11-04 收紧）

扫描（`curate._scan`）和待校对列表/统计都按 `webapp/curate.py` 的口径过滤：

- `renum_cutoff`：**有值 = 已切新口径**，老车次全部出范围（扫描按 `MAX(routes.date) >= 切换日`，
  列表按 `curate.date >= 切换日`）；
- `renum_phase1` / `renum_phase2`：**页面上两个勾选框**（数据校对页顶部「车次改号」）。
  阶段一 = V/N/Z/Y（普速）；阶段二 = G/T/K/D/C/S/X（动车）。勾上才纳入，**两个都不勾 = 清单为空**
  —— 这样在切换日之前就能先把口径切过去，等新号在预售期里出现再勾。

> 之前用过 `renum_new_letters` 白名单（阶段二一把梭）。2026-11-04 改成两个阶段开关，
> 因为用户要的是「分两次勾选，把更新后的车次列进来」，而不是跑脚本改白名单。
> 旧键已在切换日命令里清掉。

老车次的待校对行同时清掉，扫描也不会再复活它们。没跑过切换日命令 = 不过滤（改号前的老行为）。

### 4.3 切换日命令

python scripts/renumber_cutover.py --phase 1 --date 2026-11-25             # 落库（勾选不动）
python scripts/renumber_cutover.py --phase 1 --date 2026-11-25 --check 1   # 顺手勾上阶段一

幂等可重复跑；配置即刻生效（不用重启）。回归：`scripts/test_renum_cutover.py`（22 项）。

**2026-11-04 已提前按 11-25 口径跑过一次**（用户要求「现在就可以按 11-25 的版本处理」）：
清掉 `train_override` 54 条、`curate` 12779 行，`renum_cutoff=2026-11-25`，两个阶段都未勾。
备份：`data/backup/renum-cutover-20261104/`（`rail.db`、`train_override.json`、`curate.json`、

### 4.4 数据语义备忘

- 新 T/K/D 与旧 T/K/D 含义完全不同，**禁止用字头推断车种/速度**去解释历史数据
  （`collector._detect_type` 只是把首字母存进 type，展示层面无碍；将来若有按字头推属性的逻辑要按日期分时代）。

## 5. 2026-11-11 实测：新车次「下载完查不到」已定位并修复

用户反馈：「今天已经开始可以下载 2026/11/25 车次更新后的新车次代码 V/N/Z/Y，
应该已经可以查找到了，但是下载完没有」。

### 5.1 数据侧证据（只读核实）

| 检查 | 结果 |
| --- | --- |
| 12306 搜索 `V1` / `N1`，`date=20261111` | 0 / 0 条 |
| 12306 搜索 `V1` / `N1`，`date=20261125` | **200 / 89 条**（`V10`、`N10`、`N121` …） |
| 本地 `trains` 11-24 → 11-25 | 14856 → 12850，**少 2038 趟**：K 1262 / 纯数字 293 / Z 266 / T 174 / C 16 / D 16 / G 7 / Y 3 / S 1，正是阶段一要换号的普速车 |
| 本地 V/N/X/B 字头（全部 15 天） | **0 条** |

即：12306 已经按 11-25 切换日展示新号（与第 1 节时间线一致），本地却把旧普速
丢掉了、新号一个也没收进来。

### 5.2 四个根因（都在 `collector.py` 的「刷新车次全集」链路）

1. `enumerate_trains(job, job.date)` 只搜**连跑起始日 = 今天**；改号新车次只在
   11-25 及以后开行，用今天去搜永远 0 条。
2. `TRAIN_TYPES` 白名单只有 `G D C Z T K S Y N`，没有 V/X/B；而且 **`N` 被当作
   「纯数字车次」的代号**，`_prefix("N", n)` 只发 `1..9`，`N1..N9` 从来不发。
3. `_detect_type()` 拿白名单卡首字母，即使搜索回包里出现 V/N/X/B 也会被丢掉。
4. `_save_trains()` 一律写 `date=job.date`：就算搜到新号也登记在今天，
   `curate._era_where/_era_having` 的 `date >= renum_cutoff` 仍筛不到。

另外，`collect_log` 显示 11-11 07:55 最近一次单独刷新只拿到 **682 趟**且任务
停在 `paused`（06:53 那次是 15331 趟）——这次刷新被 403 限流打断，也是「下载完
没有」的叠加原因。

### 5.3 修复口径（详见 `docs/PROJECT-CONTEXT.md` 第 41 条）

- `enum_dates(date, future=True)`：起始日 + **预售窗口最后一天**（今天 +14 天 = 11-25），
  切换日只要落在窗口内就必然覆盖；两个日期各发一遍 `enum_prefixes()`
  （12 字母 ×9 + 数字 9 = 117 词），顶到单页上限的细分仍用同一日期。
- `TRAIN_TYPES` 加入 V/N/X/B，`N` 恢复成真字头；纯数字由 `DIGIT_PREFIXES` 独立生成。
- `_detect_type()` 收任意字母，只存首字母；纯数字沿用历史 `"N"`，不按它推车种。
- **结果按搜索日期分别写 `trains`**：11-25 的新号登记在 11-25，随后
  `download_stops()` 会抓它们的经停站，`curate` 才筛得到。
- 下载面板新增 `#dlEnumFuture`「也搜预售最后一天（改号新车次）」，默认勾；
  可关掉省一半请求（`future=0`），但会漏掉切换日新车次。
- 列车位置地图车种筛选加 V/N/Y/X/B（中性标签），「其他车种」不再把它们算进去。
- 回归 `scripts/test_renum_enum.py` 56 项 + `test_chain.py` 数据驱动更新。

### 5.4 要看到新车次，还要两步（口径由用户拍板，脚本不代改）

1. 数据下载页保持「**先刷新全集**」+「**也搜预售最后一天**」两个勾选，
   点「一键连跑」重跑一次（刷新全集这一步最慢、最容易被 403，别中途停）。
2. 数据校对页顶部「车次改号」勾上「**阶段一 · 普速（V/N/Z/Y）**」，再点
   「重新扫描」。当前 `renum_cutoff=2026-11-25` 但 `renum_phase1=0` /
   `renum_phase2=0`，**两个都不勾时清单按设计就是空的**（第 4.2 节）。

### 6.3 「勾了阶段一却一趟也没有」根因与修复

- **根因**：`curate` 表是旧的（只有 1 行），勾阶段一只是 `set_renum` + `cuLoad()`，
  只重读旧表、**不触发扫描**；扫描要另点「重新扫描」。11-25 的 V/N/Z/Y 经停数据
  其实早在 `routes` 视图里（N112 / V1000 / Z47 / Y9 = 1168 趟），`summarize()` 也
  全部算得出，只是没人扫进 `curate`。
- **修复**：`app.js` 的 `cuRenderEra` 保存回调里，切换阶段后自动 `POST /api/curate/scan`
  再 `cuPoll()`，扫完自动载入新清单——勾上阶段一就能直接看到车，不用再手动点扫描。
- **实测**（2026-11-11）：手动跑一次扫描 27 秒完成，`scanned=1168`、`todo=828`，
  `/api/curate/list` 返回 V3670（固安→北京丰台）等，起讫站齐全。
