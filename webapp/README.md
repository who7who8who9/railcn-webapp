# railcn webapp — 12306 车次查询 + 地图行程

把仓库根目录那套采集脚本整合成一个本地网页：输入车次就能看经停站、时刻表、线路走向，
并按时刻表推算列车此刻在地图上的位置。零第三方 Web 框架，只复用原有的 `trainclaw.py`。

├─ config.py                  ← 原样复用（API 常量 / 字段索引 / 座位映射）
├─ trainclaw.py               ← 原样复用（TrainAPI 客户端 + 解析函数）
├─ collect_trains_p2.py       ← 原样复用（批量采集车次清单）
├─ collect_routes.py          ← 原样复用（批量采集经停站）
├─ cnrail_data_v2.xlsx        ← 车站 / 铁路线 / 站点-线路关联 原始底表

## 快速开始

```bat

start.bat

:: 方式二：命令行
cd webapp
python server.py --port 8686 --open
```

打开 <http://127.0.0.1:8686/>。

## 功能

| 模块 | 说明 |
|---|---|
| 车次详情 | 输入 `G1` 回车 → 经停站时刻表（到/发/停留/里程）+ 地图线路 |
| 站站查询 | 输入起终站查实时余票（席别 / 票价 / 余票数），点一行直接看该车次行程 |
| 位置推算 | 按「运行时长」把时刻表换算成绝对时间，在相邻两站间按时间比例插值定位 |
| 时间轴 | 自绘时间条（不依赖原生 range，Chrome/Edge 一致），可拖拽/点击/方向键定位；跨日车次在时间条上按自然日分段并标零点刻度；**条上标出全部停站的站名与时刻**（见下） |
| 地图 | 腾讯地图 GL JS（需自备 Key）；无 Key 时自动降级为无底图示意模式 |
| 车站 / 线路 | 查车站（路局 / 电报码 / 服务类型 / 连接线路）或线路（途经站点 + 累计里程），点线路名跳转；线路地图默认按 **OSM 真实走向** 画，可一键切回站点直连 |
| 数据下载 | 列出**含当日共 15 天**的日期，选一天批量下载当天**全部车次 + 经停站**，可暂停/续传/导出 JSON·CSV |
| 历史数据 | 已落库的全部日期（含下载窗口之外的更早日期）都能翻，按车次/始发/终到检索、点开看经停站、直接导出 |
| 跨日显示 | 车次详情区分第 1/2/3 日：头部行程带 + 跨零点分隔行 + 时刻旁 `+1`/`+2` 角标；HUD 与时间条均带日期 |
| 数据校对 | 扫全库车次标出「经由认不全 / 里程只能估算 / 缺坐标」，按问题筛选逐条补全；**自动推断的经由只是参考，确认后才写进正式库**；同起讫点的其它车次会连同**停站详情**列出来，勾哪趟就同步给哪趟（各存一条自己的校正，见下文「同起讫点车次」）；**每趟车的所有经停站都能改经纬度**（不只缺失的），两格都有粘贴拆分：`经度:126.576636,纬度:42.038926`、`126.576636,42.038926`、`126.576636E 42.038926N`、`126°34'35.9"E` 都认，顺序随意；手工值优先于自动结果，随改随生效 |

## 数据是怎么来的

1. **车次清单**：`collect_trains_p2.py` 用前缀搜索枚举全国 1.6 万趟车 → Excel
2. **经停站**：`collect_routes.py` 按 `train_no` 逐趟拉 → Excel（也可网页内实时按需拉）
3. **导入本地库**：`python tools/import_data.py`
4. **车站坐标**：12306 不提供经纬度，用 OSM 铁路站点数据匹配站名
   ```bat
   python tools/build_coords.py          :: OSM 导出 → station_coords.json（93%）
   python tools/fill_missing_coords.py   :: 残留缺失用 Overpass 补（98.6%）
   ```

> 网页查询优先读 SQLite 缓存；缓存未命中才向 12306 实时请求 1 次并写回。
> 所以第一批车次慢 1~2 秒，之后是本地毫秒级。

## cnrail 数据层（车站 / 线路 / 里程）

`cnrail_data_v2.xlsx` 补齐了 12306 完全不给的三样东西：车站档案、线路站序、**真实里程**。

```bat
python tools\xlsx_to_json.py        :: Excel → data\*.json（仓库根目录下）
```

| JSON | 内容 |
|---|---|
| `cnrail_stations.json` | 7579 站：中英文名、类型、行政区、经纬度、所属路局、电报码、服务类型、连接线路 |
| `cnrail_lines.json` | 417 条线：途经站点（有序）+ 每站累计里程 + 线路色 + `kmReliable` |
| `cnrail_index.json` | `{站名: [lat, lon]}`，前端/脚本直接取坐标 |
| `cnrail_meta.json` | 生成时间、坐标修正模型、覆盖率统计 |

**两个坑，脚本里都处理了：**

1. **坐标整体偏移**：原表经纬度是 `data = s × true + t` 的仿射变换结果
   （s≈1.016/1.012，t≈−5.12/+1.11），直接用会把北京南画到山西。
   用本地 OSM 车站坐标做稳健回归反解，残差中位 0.0005°（约 50 m）。
2. **站间距列不一定对齐站序**：部分线路的「站间距」个数少于站点数，按位置解析会错位。
   用「里程 ÷ 相邻站大圆距离」即弯曲系数校验，只保留 0.95~1.5 的线路（231/417）参与里程推算。

**里程怎么用**：把一趟车的相邻两站拿去线路表里查同线里程差，命中就用实测值；
未命中的区间按本趟已命中区间的弯曲系数（默认 ×1.12）折算。
结果在页面上标 `实测里程` / `部分实测` / `里程估算`，鼠标悬停可看匹配了哪几段。
G1 北京南→上海虹桥 因此从「直线 1176 km」修正为 **1318 km**（实际运营里程）。

**路径展开**：相邻两站若同处一条线，就把该线中间的站插进折线，
所以地图上是沿线的真实走向，而不是站与站之间的直线。列车位置也按里程在这条折线上取点。

## 按日期批量下载（数据下载页）

「数据下载」页签列出**含当日共 15 天**（今天 ~ 第 15 天），选中一天即可批量抓取当天全部车次与经停站。
窗口之外的历史数据不会丢：到「历史数据」页签照样能检索、查看、导出。

**为什么不是靠「12306 搜索接口枚举车次」**：那个接口限流极凶，几百次并发请求就会 403 封几十分钟。
这里利用一个更可靠的事实——**`train_no` 是车次的固定内部编号，跨日期不变**：

```
本地车次全集（17,222 条 code + train_no）   ← 来自历史采集，一次建好长期复用
        ↓ 对目标日期逐个查 queryTrainInfo
有经停站  → 说明当天开行：写 trains + routes 两张表
无经停站  → 说明当天不开行：写 day_skip 表，续传时不再重查
```

所以**只有第一次需要「刷新全集」**（走搜索接口，单线程 2 秒间隔，遇 403 自动冷却重试），
之后每天开跑都不碰那个接口。

| 机制 | 说明 |
|---|---|
| 断点续传 | 每批 40 条落库；随时可暂停，重启服务后点「继续」接着下 |
| 并发 | 1~8 线程可选，默认 6；单线程内每次请求间隔 0.45 秒 |
| 自适应退避 | 连续失败 5 次把间隔 ×1.35（上限 3 秒）；连续 25 次或遇到 403 自动暂停 |
| 全量核对 | 每天照抓全量（不抓就不知道有没有变），但**只有停站真变了才新存一份**；导出文件另存 `data/exports/` |
| 导出 | `railcn_<日期>.json`（完整结构）或 `railcn_<日期>_stops.csv`（停站明细，Excel 可直接打开） |

实测规模：一天约 **1.7 万趟候选**，实际开行 1.3~1.4 万趟，6 线程约 25~35 分钟跑完。

> 注意：`trains` 表里「已确认开行」只算拿到了经停站的车次；只被枚举进来但没验证的不计入。

#### 经停站怎么存：一天一条指针

同一趟车停站不变时，12306 每天返回的经停站 JSON 是**逐字节相同**的（里面没有日期字段）。
按 (车次, 日期) 各存一份，25 天下来 24.6 万行里 95% 是重复的（520 MB）。所以拆成两张表
+ 一个只读视图，视图名还叫 `routes`，老的 SQL 一行都不用改：

| 对象 | 内容 |
|---|---|
| `route_tpl` | 一趟车的一份停站表，`UNIQUE(train_no, fp)`；`fp` 是停站指纹（站序 + 到点 + 开点 + 车次号），`hits` 记被几天复用 |
| `route_day` | `(train_no, date)` → `tpl_id`，一天一条指针，几十字节 |
| `routes` | 视图：`route_day ⋈ route_tpl`，字段与老表一致（`train_no / date / code / raw / updated_at / tpl_id`） |

- **每天照抓不误**：新的一天照样请求 12306，抓到后算指纹；一致就只写一条指针，
  `route_tpl` 不动 —— 「核对是否一致」这件事照做，只是不再存冗余副本。
- **变了才新版本**：`route_day.tpl_id` 从哪天开始换，就是「这趟车从哪天起停站变了」。
  `routestore.versions(conn, train_no)` 给出时间线（首末日期、天数、站数）。
  本库现有 244 趟车在 25 天里变过（调图 / 临时加停站 / 缩短区段）。
- 指纹故意**不含** `wz_num`（余票占位）、`service_type` 这类随日期变又不展示的字段；
  含 `arrive_day_diff`，所以跨天到达的站变了照样敏感。
- 写入统一走 `routestore.put_route()` / `put_routes_for_date()`（采集、单趟抓取、Excel 导入
  三条路径都接了）。**`routes` 是视图，不能直接 INSERT**。
- 老库迁移：`python scripts/migrate_routes_dedup.py`（先看统计）→ `--apply` 真迁
  （`--vacuum` 顺带回收文件空间）。本库：815 MB → 141 MB，经停站部分 520 MB → 27 MB。

### 一键连跑（刷新全集 → 按天依次下）

页面左上角「▶ 一键连跑」= 一条流水线，点一次就把整件事跑完：

```
刷新车次全集（12306 搜索接口，约 5~10 分钟，只在开始时做一次）
   ↓
第 1 天（今天）→ 第 2 天 → … → 第 15 天
```

- **队列按天串行**：上一天跑完才开下一天，不会同时抓多天（并发在单天内部，线程数照旧可选）。
- **重复点不重复跑**：已经下完的日子进去只剩 0 趟待处理，会瞬间跳过，所以每天点一次也不会浪费时间。
- **随时暂停**：「⏸ 暂停连跑」只停在当天，进度落库；再点「▶ 继续连跑」从这一天接着跑，
  **不会重刷全集**（除非中断发生在刷新全集那一步）。
- **进度看得见**：横幅显示「连跑中 3/15 · 第 3 天 10-28 周三 · 下载经停站 · 已跑 42 分钟」，
  列表里正在跑的那天可单独暂停，其余日子显示「排队中」。
- **断点跨重启**：连跑进度写进 `rail.db` 的 `chain_run` 表，服务重启后横幅变成「连跑已暂停」，
  点继续即可接上。
- **限流自保**：某天因 403/连续失败被自动暂停时，整条连跑一起停下并给出提示，不会空转。

#### 连跑是不是更容易被封？

单次请求速度没变，但连跑把「跑一天就停」拉成「连着跑几小时」，暴露窗口大了十几倍，
不加刹车确实更容易撞到 12306 的限流。所以加了三条：

| 刹车 | 行为 |
|---|---|
| 换天冷却 | 一天跑完停 60 秒再开下一天；上一天有失败、或刚被限流，冷却 180 秒 |
| 退避记忆不归零 | 被限流拉长的线程间隔（最高 3 秒）存进进程内的 `_THROTTLE`，**换天 / 继续**都继承；顺利时再慢慢降回 0.45 秒，半小时彻底没事才恢复原速 |
| 全集默认不刷 | 「刷新全集」要发 **800 个搜索请求**（81 个一位前缀 + 顶到单页上限的前缀再细分 10 个），是全流程最容易被 403 的一步。连跑只在「本地全集不足 1000 趟」或「一周没刷过」时才刷；其余情况直接跳过，并在横幅写明原因。要强制刷仍可在某天详情点「刷新全集」 |
| 只细分必要的词 | 搜索接口单页上限 200，只有返回 ≥195 条的前缀才继续细分，避免为没顶到上限的词白跑请求 |

> 一句实话：枚举这一步的请求量砍不掉（一位前缀几乎全都顶到 200 条，必须细分），
> 能改的是**别每次都做**。数据下载真正的主力是「按 train_no 查经停站」，那个接口宽容得多。

页面上的「并发线程」照样是最终速度旋钮：2 线程最稳，6 线程最快。

> 顺带修掉一个老口径问题：`universe()` 与「待处理」统计原来各取一行的 `train_no`
> （同一车次号在不同日期可能登记了不同编号），导致页面显示待处理 2377 实际只跑 218。
> 现在两处统一取 `MAX(train_no)`，待处理数与真正要跑的趟数一致。

## 历史查询（历史数据页）

已落库的数据可以按两种方式查，全部读本地 `rail.db`，不再碰 12306：

| 视图 | 能回答什么 |
|---|---|
| 车次查询 | 某车次在日期段里哪几天开行、哪几天不开行；点开行日看当日停站时刻。同号调图会拆成 v1/v2 两个版本，见下文 |
| 大类统计 | 按日看 G / D / C / K / … 各开行多少、不开行多少（行=日期，列=大类） |

两个视图的日期段默认都是**今天前后各 7 天**（未来几天没下数据就显示「无数据」），
另有「前后 30 天」「全部」按钮，也可以手填任意区间（单次最多 400 天）。

### 开行 / 不开行怎么判定

三张表交叉，从上往下命中即止：

| 依据 | 结论 |
|---|---|
| `routes` 有这天的经停站 | **开行**（停站可查） |
| `day_skip` 有这车这天 | **不开行**（下载时明确查不到经停站） |
| `trains` 有这车这天 | **开行**（枚举到了，停站还没下） |
| 那天枚举过车次（`trains` 非空）但没这车 | **不开行**（页面标「推断」） |
| 那天只下了停站、没枚举车次 | **无数据**（不敢推断，怕把没跑完的日子说成停运） |
| 那天完全没有采集 | **无数据**（不进统计） |

口径是 12306「当日可售车次」：当天开行但不放票的车次查不到，会计入不开行。

### 同一车次号 ≠ 同一趟车（调图）

车次号会被复用：调图、缩线、改号、套跑之后，同一个 `G6131` / `C177` 可能换了一条完全不同的
径路、换了一组停站、换了一套时刻。库里现成的例子：

| 车次 | 早期 | 之后 |
|---|---|---|
| `C177` | 07-04 商南 → 西安，6 站 | 10-22 起商南 → 宝鸡，11 站；10-29 起又缩回西安 |
| `G6131` | 岳阳东 → 广州，编号 …3D | 10-23 起岳阳东 → 佛山，编号 …3G；10-30 起又改回广州 |
| `G2068` | 10-26~10-30 27 站 | 10-31 起 28 站（加站） |

所以日历不会假装它们是一趟车：

| 标记 | 含义 |
|---|---|
| 格子角标 `v1` `v2` + 版本色边框 | 按 `(train_no, 始发, 终到)` 把开行日分成的不同方案；顶部列出每套方案的日期与起讫 |
| 汇总「该号 N 套方案」 | 区间内不止一套走法，**跨版本不能直接比停站和时刻** |
| 格子「改点」 | 同一方案内，这天的停站/到发时刻和上一个开行日不同（加了站、减了站或改了点） |
| 版本清单里的 `⚠` | 这套方案的车次信息（`trains` 起讫）和停站表（`routes` 首末站）互相矛盾，可能抓到了同号另一趟车 |
| 校对页「该号有 N 套走法」 | 经由/里程校正**按车次号保存**，会同时作用到其它日期的运行，改之前先确认在校哪一套 |

判定用两个指纹：版本指纹 `(train_no, start_sta, end_sta)`，停站指纹 `站名 + 到达 + 出发` 逐站串起来。
两个都来自已落库的数据，不额外联网。

### 同一趟车的两个车次号（换向换号）

中途换向的列车会在换向站改车次号（上下行互换），12306 的经停站数据里**每一站都带自己的
`station_train_code`**，所以一趟车会同时挂着两个号：`4355`（四平→双辽段）和 `4358`（双辽→通辽段）。
车次清单里它们也是两行（`train_no` 相同、起讫与站数一样），以前当成两趟车，各点一次才发现是同一趟。

现在三处都按「一趟车」显示：

| 位置 | 显示 |
|---|---|
| 车次详情头部 | `4355/8` + 标签「中途换号」，下面一行写明「同一趟车 4355/8：双辽 起 4355→4358」 |
| 站序表 | 换号那一站旁边挂 `4355→4358`（hover 有说明），一眼看出在哪换的 |
| 车次列表 / 校对清单 | 两行合成一行，写 `4355/8`；校对页两行都挂同一个写法，免得当成两趟车各校一遍 |

写法规则（`railcore.code_label()`）：主号取**始发站用的那个号**（`routes` 里第一站的
`station_train_code`），其余号只差末一两位时按铁路惯例缩写 —— `4355+4358 → 4355/8`、
`K545+K548 → K545/8`、`D7931+D7934 → D7931/4`；差得多就写全（`G1234+G5678 → G1234/G5678`）。

判据用 `trains` 里**同一个 `train_no` + 同一天 + 起讫站与站数一致**，加上经停站的
`station_train_code` 确实变了；只有 `train_no` 相同不算（上一节那种同号不同趟的情况，`train_no` 反而不同）。
接口上：

- `GET /api/route` 多返回 `codes`（按出现顺序）、`codeLabel`、`codeSwitches`（`{i, at, from, to}`），
  每站多一个 `trainCode`
- `GET /api/trains` 每项多 `codes` / `codeLabel`，同一趟车的两个号已合并（搜 `4358` 也能搜到 `4355/8`）
- `GET /api/curate/list`、`/api/curate/detail` 多 `codeLabel` / `codes`
- 历史数据页仍按**单个车次号**看（那页关心的是这个号在哪些日期开行、怎么变的）

### 大类统计的两个数

明细是按日的：一行一天、一列一个大类，格子上排是当日开行趟次，下排灰字是不开行趟次；
最后两列是当天的开行 / 不开行合计，表尾一行是整段的合计。

| 字段 | 含义 |
|---|---|
| `openTimes` | 覆盖日里每天开行趟数之和（车次·日） |
| `skipTimes` | 每天「该大类全库车次数 − 当日开行」之和（车次·日） |
| `pool` | 全库登记过的该大类车次数，也就是 `skipTimes` 的分母 |

所以「不开行」回答的是「全国这类车里，这天没开的有多少趟」，不是「开行数的反面」。
`pool` 包含已停运车次——这是有意的：要看「登记过的车这天开了多少」。
某天没下完（枚举车次数不到最全那天的 75%）会在汇总行用橙色标出「数据不全」，
那天的 `skipTimes` 会虚高，不要拿来横向比较。



## 经由推断与人工校对

### 自动推断：三档证据，强的先说话

`cnrail.infer_via()` 逐对相邻站判断「这一段走哪条线」，按可信度取最强者：

| 档 | 依据 | 说明 |
|---|---|---|
| `km` | 线路里程表 | 两站同线且站序正确、里程差合理 —— 最可靠，通常说明该段确在此线上 |
| `pos` | 线路站序 | 两站都出现在该线站序里且前站在前，不要求相邻（跳站车次也能认） |
| `lines` | 车站档案 | 两站「连接线路」的交集 —— 最弱，只作兜底 |

同一档里优先选**与上一段连续**的线路（`京广高速线` 与 `京广线` 视为同族），
避免在两三条并行线之间来回跳。输出是**结构化区间**而不是线路名列表：

```json
[{"line":"峰福线","from":"福州","to":"武夷山","i0":0},
 {"line":"京九线","from":"南昌","to":"商丘","i0":6}]
```

区间之间若有一对站认不出，会单独给出 `unknown: [{"from":"武夷山","to":"南昌","i0":4}]`，
界面上就落在链路的正确位置（而不是全部堆到末尾），编辑行里也直接变成「线路名待填」的空行。

> 为什么必须做这一步：很多车次在里程表里一段都匹配不上（`郑州`、`洛阳` 这类枢纽站
> 恰好不在「里程可信」线路的站序索引里，全库 7579 个站只有 2426 个有站序），
> 光靠里程算经由会得到空结果。补上后两档后，K3、T197、Z21 这类车次都能认出主要经由。

### 人工校正：存下来，优先用

| 表 | 内容 |
|---|---|
| `train_override` | `code`（主键，按车次不按日期）、`via_json`、`total_km`、`seg_km_json`、`note`、`source`（manual 逐趟校正 / sync 同起讫点同步）、`src_code`（同步自哪趟）、`based_date`（校正依据哪一天的站表）、`updated_at` |
| `coord_override` | `name`、`lat`、`lon` —— 车站坐标人工修正（**任何站都能改**，不限于缺坐标的）。改完会套进 `cnrail` 车站表，线路页地图、站间里程、资料库线路图一起生效，不用重启 |
| `line_override` | `name`（主键，线路名）、`seg_km_json`、`sta_km_json`、`stops_json`（人工站序，`[{name, km}]`，null = 用档案站序）、`total_km`、`note`、`updated_at` —— 线路里程 / 站序人工校正 |
| `line_custom` | `name`、`stations_json`、`note` —— 用户新增的线路（档案里没有的） |
| `station_custom` | `name`、`lat`、`lon`、`lines_json`、`tele`、`bureau`、`note`、`type`（车站/线路所）、`source`（manual 自建 / line-fill 线路补全）、`alias`（线路里的原写法）、`coord_src`（osm/manual）—— 用户新增 + 线路补全的车站 |
| `curate` | 全量扫描结果：每趟车的经由 / 里程 / 缺坐标摘要与问题标签 |

`build_route_payload()` 里自动结果算完后再套人工值：

- 有 `via_json` → `viaLines` / `viaSegs` 整体替换，`viaSource=manual`，不再显示缺口
- 有 `total_km` → 各站里程按 `total_km / 自动末站里程` 等比缩放，`kmMode=manual`
- 有 `seg_km_json` → **逐段锁死**：`{"0":205,"2":230}` 表示「第 1 段（第 1 站→第 2 站）205 km」、
  「第 3 段 230 km」；手填段用填的值，其余段沿用自动值，从 0 开始重新累加各站累计里程。
  若同时又填了 `total_km`，则只把**没手填的那些段**按比例缩放到 `total_km − 手填段之和`，
  这样既能锁定已知的精确区间，又能保住全程总量

`seg_km_json` 的键是「区间序号」而不是站名，因为区间序号在同一趟车的上下行、不同日期里都稳定，
站名偶尔会因经停变化（加开 / 甩站）而错位。

### 自动推断的经由要「确认」才进正式库

`build_route_payload()` 每次查询都按线路库现算一份经由 —— 那是**算出来的参考结果**，
不是库里的数据。正式库（`train_override`）里只有确认过的，而「确认」有两条路：
逐趟人工填，或者从同起讫点车次同步过来。**两条路都算「已校正」**，区别只在 `manual.source`：

| 来源 | `viaSource` | 进正式库 | 算不算已校正 | 界面 |
|---|---|---|---|---|
| 逐趟人工补全 / 确认 | `manual`（`manual.source=manual`） | 是 | 是 | 绿标「已校正」 |
| 从同起讫点车次同步过来 | `manual`（`manual.source=sync`） | 是 | 是 | 绿标「已校正 · 同步」，悬停看同步自哪趟 |
| 自动推断 | `auto` | 否 | 否 | 灰标「自动推断」「待确认」 |

所以统计条里「其中同步」是「已校正」的**子集**，两个数不能相加；
`filter=manual` 含同步的，`filter=synced` 只是把同步进来的那批单独捞出来回看。

校对清单里凡是 `via_source='auto'` 的都挂「待确认」，`filter=pending` 只看这一类；
编辑器「确认自动结果并入库」把整趟认全的自动结果一次确认为人工并保存，
也可以在某一段点一下「自动」标签单段确认。

### 同起讫点车次：列出来，人工勾选同步

同一对起讫站常有几十趟车走同一条径路，一趟趟填是重复劳动；但**同 OD 的车走法未必一样**
（`沈阳→丹东` 既有走沈丹线的普速，也有走沈丹客专的动车，这类混合组全库 515 组），
所以不做「自动沿用」，改成在校对页把候选列出来让人勾：

- 编辑器里「同起讫点的车次」列出同 `from → to` 的其它车次，每行给出站数、起止时刻、
  与这趟车的停站重合度、它现在的经由；点「停站详情」展开完整站序（到 / 发时刻、跨日标记）
- **站序按 `train_no` 取，不按车次号**：换号车（C344/5、C4326/7）整趟站序在库里只落在
  到达号 C345 / C4327 那一行，按出发号查会「0 站、没有时刻」。`route_stops_brief()` 先用
  `trains` 取这趟车的 `train_no`，再按它去 `routes` 找那一页；这样 1044 趟换号车的站数和
  到发时刻都能正常显示
- 库里确实没抓到站序的车（全库只剩 3 趟），行上标红「无停站数据」、勾选框禁用，
  在行车页打开它一次就会去 12306 抓回来；本车自己没站序时，同伴标「无法比对」而不是「重合 0%」
- **已经校正过、或从别处同步过的车次不再列出来**——它们已经定稿，摆在这里只会被误勾一次、
  被覆盖一次。卡片标题只留一句「另有 N 趟已校正，不再列出」（接口里是 `hidden` 计数）；
  同起讫点全都校正过时，卡片就只剩这一句，不再有勾选框
- 勾选后保存（`POST /api/override` 带 `syncCodes`），刚存好的经由会**逐趟套过去**，
  每趟各存一条自己的 `train_override`（`source=sync`，`src_code` 记来源车次）。
  同步是「一次性把已确认的结论复制给选中的车」，复制完各自独立，不再互相影响；
  存完这几趟立刻从候选里消失，勾选也自动作废
- **对方的每一站都在这条经由走过的路上 → 原样照抄**（`mode=direct`）：区间端点一个不动，
  连转线的所（春申南所、灭火沟线路所）也照留，**不重新落站、不重算**。
  这类车次在列表里挂「停站全在经由内」青标，一眼能看出勾了会怎么存
- 只有它停了经由**之外**的站，才按它的停站重新落站（`mode=adapt`）：端点对不上时按
  「第几站」的比例就近并入相邻段，首尾必然相接。哪种方式都会在保存提示里说明
- 只同步**覆盖全程**的经由；候选里只会出现还没校正的车次，所以不存在覆盖别人成果的情况
- 站间里程不跟着同步 —— 它按「第 i 段」记下标，站数不同就对不上

![同起讫点车次同步](../docs/curate-od.png)

### 校正和车次号绑定，并记下依据哪天的站表

`train_override` 按**车次号**存（不按日期），另记 `based_date` = 校正时依据的那一天的站表。
调图后站表变了（加站 / 甩站），编辑器头部挂「站表已变」并列出少了哪些站、多了哪些站，
提醒按新站序重校 —— 校正结论不会悄悄套到面目全非的新站序上。

### 线路里程人工校正

线路的里程来自 `cnrail_lines.json`（417 条线，其中 182 条有站缺里程、2 条没有总里程）。
「车站 / 线路」页选中线路后点「编辑里程」，改的是**这条线本身**：

- 相邻两站逐段列出，灰字是档案值，档案缺的段显示 `-`（不详），留空即沿用
- 填了就锁住该段；底部的「线路总里程」同样可改，填了就把**没手填的段**缩放到「总里程 − 手填段之和」
- 保存进 `line_override`；「全部恢复档案」清掉里程那几列（只改过站序的线保留站序，站序要撤走「恢复档案站序」）
- 同一张表里还存**人工站序**（`stops_json`）：档案线路插站 / 调站序后，`_line_with_override()` 先整份替换档案站序，
  再按这次填的累计里程重算；`seg_km_json` / `sta_km_json` 是按**下标**记的，所以改站序时会被一并清空

生效方式和车次里程不同：`railcore` 启动时把 `line_override` 灌进 `cnrail`，
`cnrail.rebuild_lines()` 用人工值重算各站累计里程并**重建「站名 → 线路里程」索引**，
所以之后车次里程配对（`refine_km` / `_pair_km_raw`）用的就是改过的数；缺口的段保持 `None`，
不会外推（界面上仍是 `-`）。人工改过的线路即使档案标着「里程不完整」也会进索引 ——
否则改完不生效，等于白填。

生效是**即时**的：payload 每次请求现算，不缓存最终结果，改完刷新详情页就是新数据。
`GET /api/curate/detail` 特地带 `use_override=False` 跑一遍，专门给编辑器显示「自动推断基线」，
改错了还能对照原来是什么。

### 车站表补全（线路里有、站表里没有）

车站档案只有 7579 条，线路 / 资料库里却出现过 1860 个档案没有的站名
（大量地方小站、线路所，档案只收了大站）。`scripts/fill_missing_stations.py` 把这些补进
`station_custom`（`source='line-fill'`），站表随之从 7579 → 9443：

```
python scripts/fill_missing_stations.py                 # 只统计
python scripts/fill_missing_stations.py --apply         # 写库（--report docs/station-fill.json 出清单）
```

- 站名来源三处：`data/cnrail_lines.json`、`line_custom`、`line_catalog_stop`（辉睿线路资料库）
- 站名按档案口径截掉尾部「站」（`上虞站` → `上虞`），原写法记在 `alias`；
  「十八站」这类地名自带的「站」不动。`线路所 / XX所` 是独立设施，**不能被 `cnrail._key` 截成 `XX`**，
  所以这类站的合并键用全名，免得把同名车站顶掉
- 坐标能对上 OSM 派生库（`station_coords.json`）的就直接填（883 个），对不上的留空，
  之后在车站详情里用「补坐标」框一行行补
- 补进来的站在详情里带「线路补全」标记，站名联想（`/api/stations`）也能搜到

### 同一个站的两种写法（站名去重）

「线路站序写『河边站』、车站库里写『河边』」这种事很容易发生：坐标补在「河边」上、
站序引用的却是「河边站」，于是线路详情缺坐标、车次经停与线路站序对不上，
看着就像同一个站存了两份。资料库带进来的线路整段站名都带「站」（东北东部铁路 93 站里 45 个），
问题更集中。

`scripts/dedupe_station_names.py` 一次修好：

```
python scripts/dedupe_station_names.py            # 只看会改什么
python scripts/dedupe_station_names.py --apply    # 真改（先导出备份到 data/backup/）
```

- 判定保守：名字本身在坐标表里的**不动** —— 黑龙江的「九站」就是带「站」的地名
- 车站表里撞名的合并成一条：坐标优先留人工录的，连接线路取并集，其余字段取非空
- 线路站序同步替换，替换后相邻重复的站并掉
- 实测：67 个写法、18 条线路 90 处、5 条车站条目；改完线路站序里不再有「XX站」
  （只剩「九站」），忻河线坐标覆盖 100%

### 12306 站表里有、线路库档案里没有的车站

`唐海南` / `曹妃甸港` / `南堡北` 这类站（唐曹线、曹妃甸港线上的站）就落在这个夹缝里：
12306 站表里有电报码（IEP / PGP / TLP）、经停缓存里也有它们（C248、C133 …），
但它们所属的线**在源数据里没有站序**（辉睿的唐曹线 `stops` 是空的），因此收不进线路库，
`cnrail` 也就没有档案 —— 以前的表现是「联想下拉能搜到、点进去却说『车站库里没有』」。

现在 `railcore.station_detail()` 在档案查不到时走 `_station_detail_loose()` 兜底：

| 字段 | 来源 |
|---|---|
| 站名 / 电报码 / 城市 / 地址 | 12306 站表（`stations.json` + `data/crtrain/data_stations.json`） |
| 坐标 | `station_coords.json` / 人工补录（跟档案站一样可以直接在详情里改） |
| 经停的车次 | `routes` 里最新一天的路由缓存，按 `"station_name": "站名"` 精确匹配（约 0.2 秒） |

详情头带「仅 12306 站表」标记，并注明「线路库里没有这个站的档案」；因为取不到「连接线路」，
改列当天经停的车次（点车次号直接跳车次详情）。站名联想同时改成**带去「站」字也能搜**
（`唐海南站` → `唐海南`），并把「唐山」和「唐山站」这类同一站的两种写法并成一条，
显示优先用 12306 的写法（不带「站」）。

> 有「连接线路」可点，当天经停的车次照旧列出（自建站的档案里没有车次数据，

### 线路真实走向（OSM · CRTrainRoute）

线路库里只有「站序 + 里程」，没有轨道走向，地图上一直是站点直连。接入
[Laide140/CRTrainRoute](https://github.com/Laide140/CRTrainRoute)（MIT）的 OSM 数据后，
每条线都能按真实轨道画：

```bat
python scripts\fetch_crtrain.py      :: 拉 32 个省级 geojson（约 142 MB）+ 站名/坐标
python scripts\import_crtrain.py     :: 归集成 data\crtrain\lines.json + geoms.json.gz
```

- 数据来源：CRTrainRoute 仓库 `data/geojson/*.geojson`（底层是 OSM 铁路线，要素带 `name` = 线路名），
  一共 **3007 条线、17.4 万个铁路要素、16.0 万 km**（上下行去重后）
- **里程怎么算的**：按线名归集后把节点量化到 1e-4°（约 11 m）建图——上下行两条平行轨在这个精度下并成一条，
  所以不会出现「京沪线 2994 km」这种翻倍；再对每个连通段取直径（两次 Dijkstra）相加。
  京沪线 1434 km（档案 1463）、京沪高铁 1296（实 1318）、陇海 1696（实 1750），误差都在 2% 内
- **几何怎么存的**：OSM 一条线被切成几千个 2~3 点的 way，先按端点相连 + 转向 < 90° 接成长折线
  （京沪线 2170 段 → 102 节），再 Douglas-Peucker 抽稀到 25 m，坐标留 5 位小数。
  落盘 `geoms.json.gz` 只有 1.4 MB
- **怎么对上线路名**：精确 → 同族（去掉 `线 / 铁路 / 高速线 / 高铁 / 客专线 …` 后的主干名）。
  同族里可能有 `京沪高铁`（1296 km）和 `京沪高速铁路`（9 km 残段）两个，取里程最长的；
  口径必须一致——客运专线不套普速线（`包西高速线` ≠ `包西铁路`）；给了已知里程时，
  几何里程不到它 35% 的残段直接排除（`潍烟高速铁路` 只剩 2 km，对不上 585 km 的潍烟高铁）。
  档案 417 条里 325 条能对上，线路资料库 844 条里 532 条能对上
- **界面**：线路详情多一张「真实走向」卡（OSM 线名 / 几何里程 / 连通段 / 桥隧数 / 与档案里程差），
  带「改站点直连 ↔ 按真实走向」开关（`localStorage['railcn.lineGeom']`）；
  线路库里查不到的线，会先翻资料库、再翻这 3007 条 OSM 线，点开就能看走向
- **被同名线挡住的情况**：搜「津霸」时库里只有「津霸客运专线」（客专 73 km），
  OSM 里另有一条「津霸线」（普速既有线 83 km）—— 库里那条直接命中，页面就停在那儿，
  不会落到「查不到才去 OSM 找」的兜底路径，另一条永远看不见。
  现在联想下拉把差集接在后面（标 `OSM 未收录`），线路详情头部下方也列一块
  「OSM 里另有 N 条相关线路」，点开就是走向，可补站收进线路库。
  差集口径（`railcore.osm_extras`）：按去掉尾缀的「核心名」比对，**客专 / 普速分开算**
  （客专收录了不代表普速线收录了）；已收录的、里程 < 5 km 的、
  同核心名但明显是残段的（不到已收录那条的 35%）、以及 `联络线 / 疏解线 / 第三线`
  这类派生线名都排除。实测 OSM ≥5 km 的线里，线路库没收录的还有 987 条
  （≥20 km 的 423 条），其中 30 条是「库里已有同核心名的另一条」，最容易漏看
- **两个数不是一回事**：线路库 417 条是「主要干线 + 站序 + 里程」的口径，
  OSM 3007 条是「按 `name` 切开的铁路要素」，包含大量联络线、疏解线、上下行分段。
  所以「OSM 里有、线路库里没有」是常态，不等于漏收 —— 值得收的是能补出站序的那部分

> 坐标系：OSM 是 WGS-84，前端统一转 GCJ-02 再画；12306 车站坐标本身是 GCJ-02，不参与这个换算。

### 新增线路 / 车站

档案只有 417 条线、7579 个站，总会有缺的（新建线路、地方小站、专用线）。

- **新增线路**：填线路名 + 沿线站序，每站可选填「自起点累计公里数」，不详就留空（存成 `null`，界面仍是 `-`）。
  校验：至少两站、站序不重复、累计里程必须严格递增、不能与档案线路重名
  - 站名下拉拿的是 `/api/stations/names`：**车站档案 + 12306 站表的并集**，和车站搜索同一套来源。
    只在 12306 站表里、档案还没收的站（唐海南、曹妃甸港、南堡北）一样能选到，输入「唐海南站」也按「唐海南」命中，不会再追加一条库外站名
  - 存进去的站名按 12306 口径归一（`唐海南站` → `唐海南`，`十八站` 这种地名不动），否则和车次经停站对不上，经由与里程也套不上
  - 保存时会把**沿线站补进车站库**（`station_custom`，`source='line-fill'`，坐标取 档案 → OSM 派生 → 人工补录 的合并值，
    电报码取自 12306 站表）：线路页的站点坐标读的就是车站档案，不补这一步，站名能显示却标「缺坐标」、地图上一个点也画不出来。
    实在没有坐标的站仍然留空，详情页头部会写清「N 站缺坐标（…），地图上不显示，可到「车站」里搜站名补坐标」
  - 老库里的自建线路不用重存：`backfill_line_stations()` 在启动线程里统一补一遍（启动后的后台线程里）
- **给只有 OSM 几何的线路补车站**：线路库和资料库都查不到、只在 OSM 里有走向的线（联络线、支线最多见），
  搜出来点进详情后有个「添加车站」——按走向反查车站库，把候选站连同沿线里程预填进「新增线路」弹窗，
  删掉不在线上的、补上空缺的，保存就成正式线路（之后能进车次经由与里程推断）。
  自建线路的详情里有「改站表」，走同一个弹窗，保存整体替换站表
- **站中间插站 / 调站序**（自建、档案线路都行）：站表每行行首有个 `＋`，点它就在这一行前面插一个空行
  （插在最前、两站之间、末尾都能插；「＋ 末尾加一站」照旧），插入后光标直接落在新行，接着打字即可。
  新行的里程格会提示相邻两站的区间（`在 12.3–48.0 之间`），留空表示这站里程不详 —— 累计里程是按站给的，
  中间插一站不影响后面已知的站。
  - 自建线路：`POST /api/line/new`（`replace=1`）整份替换站表
  - **档案线路**：详情里的按钮是「改站序」，改的是本机覆盖（`line_override.stops_json`），原始档案不动；
    头部标「站序人工」，旁边有「恢复档案站序」（点两下确认）随时撤回。
    站序一变，旧人工里程的**下标**（第 i 段 / 第 i 站）就对不上了，所以保存时会一并作废，
    改为按这次填的累计里程重算；新插进来的站同样补进车站库（`source='line-fill'`），地图上直接有点
- **新增车站**：填站名 + 经纬度（可直接粘贴「经度,纬度」或「经度:126.576636,纬度:42.038926」，
  复用校对页的拆分规则），可选填所属线路 / 电报码 / 路局。
  已在站库里的站会被拒绝，避免与 `coord_override` 两套坐标打架
- **补坐标**：车站详情里有个「补坐标」框，粘一行就能存（`POST /api/coord` 的 `coord` 字段），
  存完立刻重算相关车次，坐标值后面标「（人工）」
- 自建的条目在详情里带「自建」标记，删除按钮点两下才生效（第二次确认）

落库后走 `railcore._apply_custom()` → `cnrail.set_custom(lines, stations)`：

- 自定义线路插在 `_LINES` 最前面，同名档案线路被覆盖（保存时已禁止重名，这里只是保险）
- `rebuild_lines()` 会把它们一并算进 `_POS`，所以**新增的线路立刻能用于车次经由 / 里程推断**
- 自定义车站合并进 `_STATIONS`（已有的站只补空字段：坐标 / 电报码 / 路局 / 线路），
  再 `stations.reload_coords()` 让坐标缓存重新读，新站马上能在地图上画出来

新增线路的里程若还想改，照旧用「编辑里程」，覆盖值存在 `line_override`，与自定义线路的数据分开；
删除自定义线路时会连带清掉它的 `line_override`，免得以后重建同名线路套到旧值。

### 只有 OSM 几何的线路：怎么把车站补上

这类线（联络线最多）在线路库、资料库里都没有，只有 OSM 的一段轨道。`GET /api/line/osm/stations`
按走向反查车站库，给「新增线路」弹窗预填一份站表：

- **候选来源三路**：① 距轨道 1.2 km 以内的站；② 车站档案 `lines` 里直接写着属于这条线的站
  （几何截断也不漏）；③ 两端 3 km 以内的站（几何没画到头时补终点，这种站里程留空，由人填）
- **先说单线**：OSM 一条线常被拆成上下行两段。`railgeom.chain_parts()` 从最长的一段起头，
  往两头挑端点最近的段接上（必要时反向），接上去只是原路折回的段判为上下行复线、直接丢掉；
  端点离得太远（`gap_m`）也不再硬接，免得把两条不相干的线拼成一条
- **里程按单线折算**：源数据的 `km` 是各要素里程相加，上下行分开建要素时会各算一遍
  （赵甸联络线 10.5 km，实际单线 5.9 km）。所以补站里程和「几何比档案」的差异都用单线里程；
  `chain_info()` 同时给出 `dupKm`（判复线丢掉的）和 `dropKm`（接不上丢掉的），
  **只有 `dropKm < 0.5` 时单线里程才可信** —— 走向有缺口时页面退回源数据里程，不拿它去比档案
- 排序按沿线累计里程；同位置压着几个站时按 0.1 km 错开，免得撞上「累计里程要递增」的校验
- 站名不在车站库里的照样能填，但要去车站页补坐标才会画到地图上

### 分段线名 ↔ 整条线：缺站序的补站序，缺走向的借走向

同一个线名在两套数据里常对不齐，于是两侧各缺一半：

| 形态 | 例子 | 后果 |
|---|---|---|
| 线路库按「段」收，OSM 只有整条 | `成昆线成攀段`、`成昆线元昆段` ↔ OSM `成昆线` | 有 117 站，没有走向 |
| OSM 有整条几何，线路库里没这条线 | `成昆线`、`京哈高速线` | 有走向，一站都没有 |

`webapp/lineseg.py` 在**查询时**把缺的那一半补上，不往库里写（几何是站序的派生物，
站序还会被人工改；服务一重启就按最新站序重算）。缓存只放进程里。

**方向一：分段线借父线的走向，再裁掉两头**

`borrow_geometry(段名, stations, totalKm)`：OSM 里没有这个名字，就去要父线（`成昆线`）的几何，
再按本段首末站裁出那一截。实测 13 条能借，其中 11 条能精确裁到位：

| 分段 | 档案 | 裁出 | 分段 | 档案 | 裁出 |
|---|---|---|---|---|---|
| 成昆线成攀段 | 734 | 725.4 | 京哈高速线沈哈段 | 545 | 517.4 |
| 成昆线元昆段 | 260 | 257.7 | 京港高速线赣深段 | 434 | 422.9 |
| 京包客专线张包段 | 468 | 467.2 | 吉玉线铜玉段 | 48 | 46.9 |

裁不出来就**如实退回整条并写清原因**，不硬凑：宁西线西合段（930.9 km）的几何断成 7 截，
硬要连通得横跨 294 km 的空白，那就还是画整条 + 提示「几何断成几截，走不通」。

**为什么不用 `chain_parts()`**：它判复线用的是「接完这段会不会离起点更近」，
长干线上（京哈 1210 km）会把它该接的段全当复线丢掉 —— 成昆线只串出 313 km。
这里换成三步：

1. **复线去重**：两段首尾都对得上（正向或反向，容差 0.35 km），只留长的那条
2. **端点缝合成图**：按**连通分量**取最近的一对端点做候选边，再跑最小生成树。
   不能「每个端点就近连几个」—— 一条线常被切成十来个互不相连的分量，
   小分量的最近邻全在同一条大分量上，它自己永远连不出去（宁西线断口都在 52 km 内却走不通就是这个）
3. **走最短路**：Dijkstra 从首站走到末站，断口按直线补、里程照算并记数；
   缝合距离由紧到松试 `8 → 25 → 60 → 200 km`，里程和档案差 > 25% 的判为「借错了线」直接退整条

**方向二：只有 OSM 的线名，补一份站序**

`stations_for(OSM 名)` 两路来源：

- **线路资料库同名**（首选）：`成昆线` → 133 站（成都 → 昆明，1096 km）、`格库线` 37 站、`宁西线` 104 站
- **同前缀分段线拼接**：`京哈高速线` ← 京沈段 + 沈哈段 = 37 站

拼接只认**硬接缝**（上一段末站 = 下一段首站，或相距 ≤ 25 km）：京港高速线的商合段止于合肥北城、
赣深段起于赣州西，中间隔着 407 km 的合安、昌赣，拼起来是假的 —— 宁可拒绝并说明「中间缺一段」。
里程按段累加，站名统一成 12306 口径（资料库里的「碧鸡关站」→「碧鸡关」）。

实测 OSM 3007 条线名里 **468 条能补出站序**（资料库 463、分段拼接 5），
其中 ≥30 km 的 128 条 —— 这些正是「有走向、没站表」，补完就能进经由选取与路径解析。

**接口与界面**

- `GET /api/line?q=成昆线` → 133 站 + OSM 整条几何，标 `stopsFrom=catalog`
- `GET /api/line?q=成昆线元昆段` → 31 站 + `osm.borrowed=true` / `osm.clipped=true` / `osm.clip={from,to,km,gaps}`
- `GET /api/line/osm?q=成昆线元昆段` → 裁好的 1 段 472 点、257.7 km（不是整条 1022 km）
- `GET /api/line/stops?q=京哈高速线` → 37 站（`from=parts`），校对页选经由也能用了
- `GET /api/line/osm/list` 每条加 `stopsN` / `stopsFrom`，列表上标「可补 133 站」
- 线路详情头部：「站序来自资料库」「站序由分段拼」；走向卡片：「借 成昆线 裁出本段」+「裁出区间 黄瓜园 → 昆明东」
- 点「按真实走向」取几何时用 `osm.ask`（本段名），才会走裁剪那份；用 `osm.name` 会拿到整条

> 站名坐标指错地方时（`龙烟线龙五段` 的「龙泉北」落在 782 km 外），首末站离几何 > 30 km
> 直接判「坐标可能指错」，不裁也不硬套 —— 这类要回车站页补坐标。

### 资料库那条线挂给库内哪一条

`line_catalog.line_name` 决定线路详情页取哪条线的资料，也决定搜一个资料库线名时跳到哪条线。
认三条路：**同名** → **去后缀同族**（京沪高铁 ↔ 京沪高速线）→ **站序重叠**。

站序重叠这一档原来的分母取了 `min(两边站数)`，等于只要库内那条线的几站都落在资料库站序里就必然 100%：
**侯西线**（42 站 / 288.5 km）被挂给了 9 km 的 **陇海西成联络线**，搜侯西线出来的是「三桥 → 西安西」两站，
资料卡却又挂着侯西铁路——因为 `_CATALOG` 是按 `line_name` 建的索引，两个方向都串了。

现在：分母改成「资料库站数」，覆盖率 ≥0.6 才算；量级只卡下界，且**站数与里程同时**不到一半才判
「小线冒充大线」——只小一头的是正常分段关系（京石高铁 7 站 283.7 km 是京广高速线 42 站 2291 km 的一段），
加上界会误杀半张表。

覆盖率 0.5~0.7 那一档不做新增匹配：广佛环线→南广线、汉宜高铁→襄荆高铁全是噪音。
宁可 `line_name` 留空，查询时走 `compose_line`，用资料库站序 + OSM 走向拼出完整线路，比挂错线准。

| 修正后搜 | 站 | 里程 | OSM 走向 |
|---|---|---|---|
| 侯西线 | 42（侯马北 → 西安）| 288.5 km | 侯西线 237.7 km |
| 宁西线 | 104 | 1030.2 km | 宁西线 930.9 km |
| 同蒲线 | 101 | 865.0 km | —（OSM 只有南/北同蒲）|

### 地图：经由线路上的全部车站

`cnrail.path_stations(stops, prefer=经由线路名)` 把经停站序列展开成「线路上全部车站」：

- 相邻两站在同一条线上时，把该线中间的站补进来；里程按 `本趟车两站里程 / 该线两站里程` 的比例映射
- `prefer` 是推断（或人工校正）出来的经由线路名，命中时优先按它展开，其次才按里程比匹配
- 输出 `[{name, lat, lon, km, stop, idx}]`，`stop=False` 表示列车通过但不办客；线路所 / 中继站直接丢弃
- `path`（画线用的折线）与 `lineStops`（打点用的车站）来自同一次展开，保证点位与折线严丝合缝

前端两种地图后端都按这个画：实心蓝点＝停车站，旁边标「站名 + 发车时刻」（终到站标到达时刻）；
浅灰小点＝通过站（不标字，标了会糊成一片），点一下看里程与所属车次。

### 校对页

左列按问题筛选（待补全 / 经由全无 / 经由缺口 / 里程 / 缺坐标 / 自动待确认 / 已校正 / 同步入库（已校正的子集） / 无问题 / 全部），
右侧编辑器做四件事：

1. **分段填经由** —— 线路名是下拉选择（`▾` 展开全部线路，打字即时过滤，`↑↓` 移动、`Enter` 选中、
   `Esc` 关闭；库里没有的名字照填照存，会作为最后一项「用这个名称」出现），站名跟着线路走：
   取这条线的完整站序（含不停车的通过站），**线路所 / 乘降所 / 中继站也一并列出**，右侧标一句
   「线路所」——沪春线的春申南所、宝成线的灭火沟线路所都能选；命名线路的站序里漏掉的节点，
   用资料库的同名站序按前后邻居位置补回来（客运站顺序一个不动）；只存在资料库的线路
   （银西高铁之于银西高速线）也能出站序。线路名哪都对不上时退回这趟车的经停站
2. **站间里程逐段改** —— 按相邻两站列出全部区间，灰字是自动值、留空即沿用，填了就锁住这一段；
   行尾显示与自动值的差（`+9.0` / `-5.0` / `=`），改了哪段一眼看得见，`↺` 单段还原、
   「全部恢复自动」整列还原；底部的合计、以及「经停站与里程」里的各站累计值都随输入实时重算
3. **总里程** —— 可留空；填了就对「没手填的段」做等比缩放
4. **改任意车站的经纬度** + 写备注

保存前会校验：

- 每段必须有线路名
- 区间首尾相接（「第 N 段到 X，第 N+1 段却从 Y 起」会直接指出来）
- 站名必须在这条线路的站序里（线路名认不出对应线路时，必须在这趟车的经停站里）
- 总里程与自动值差 25% 以上时提示确认
- 手填的站间里程与自动值差 3 倍以上时提示核对（只提示，不拦保存）

自动推断的结果在编辑器里是「自动」标签的虚拟段 —— **不确认就不入库**。「确认自动结果并入库」
把整趟认全的自动结果一次确认为人工并保存；有缺口时按钮置灰，先补全再说。
保存时如果勾了「同起讫点的车次」，刚存的经由会逐趟套过去（见上文「同起讫点车次」）。

全量扫描约 11800 趟、4 分钟（约 20 ms/趟）。扫描时**先算后写**、攒 40 条一个短事务落盘，
否则一边算一边挂着写锁，用户点保存会被锁到超时。

#### 线路库刚改过怎么办

自动经由是**读的时候**按线路库算的，但清单摘要（`curate` 表）、线路名下拉、线路站表都是缓存的。
所以新加完线路回到校对页，页面上可能还是旧结果。三处配合着解决：

- **重算自动经由**（「自动推断的经由」卡片右上）—— 重载线路库（`railcore.reload_library`：
  自建线路 / 车站 / 人工坐标重灌进 cnrail）→ 重算这趟车的自动基线 → 顺手刷新清单里这一行
  （`POST /api/curate/refresh`）。有未保存的手工填写会先弹确认，重算不会悄悄丢掉你的输入。
- **点选加入** —— 自动链上的每一段都能点：点一下收进下面的手工列表（成为人工段），再点一下撤回。
  自动推断失败的缺口另外列「候选线路」：缺口**前后已识别段用的线**排第一（缺口多半就是那条线中间
  断了一截），其余按「覆盖这趟车多少个经停站」排序，再补上缺口两端车站自己所在的线
  （线路表里缺了连接段时两站永远不共线，只报共线等于什么都不给，这类候选会注明要让改起止站）。
  点一下就在手工列表里填好这一行，位置按经停顺序插入。
- **线路 / 车站跟着库走** —— 每次打开编辑器都重拉线路名清单；站名框打字时还会去 `/api/stations`
  现查一遍（下拉里标「车站库」的就是现查来的），所以刚在「+ 线路 / + 车站」里加的东西马上能选到；
  新增线路保存后前端的线路名、线路站表缓存一并失效，「新增线路」弹窗的站名库也每次打开重拉。

### 车站坐标编辑

「车站坐标」卡片列出该车**全部**经停站，不是只列缺坐标的——档案里的坐标本身也可能错
（同名站串号、老数据偏移），能改才有意义。每行显示：序号 + 站名、纬度、经度、
来源徽标（`档案` / `人工` / `缺失`）、保存、还原。

- 经纬度按 **WGS-84** 填（与 OSM 一致），前端再换算成腾讯地图用的 GCJ-02，不用自己转
- 支持**成对粘贴**：把 `115.67135293489208,37.32526706163806` 粘进任一格（经度在前、纬度在后），
  自动拆成两格；中文逗号 / 分号 / 空格分隔都认，`纬度,经度` 反着写也能靠取值范围自动纠正
- 保存写 `coord_override`，**立即失效坐标缓存**并重算引用该站的车次；
  地图定位、线路走向、里程插值下一次请求就是新值
- `还原` 删掉人工值，回到车站档案原值；档案里也没有就退回「缺失」
- 卡片支持按站名筛选、勾选「只看缺坐标」，缺失行用红底标出
- 保存只重画当前行，不会冲掉你在别处正在编辑的经由；切回车次详情时会静默重拉一次

> 撤销坐标有个坑：`refresh_station()` 原本靠 `curate.missing_json LIKE '%站名%'` 找受影响车次，
> 撤销后该站已不在缺失清单里，一行都匹配不到、清单上的缺坐标数不会回退。
> 现在匹配不到时回退到 `routes.raw LIKE '%"station_name": "站名"%'` 反查
> （全表扫描约 0.3 s，撤销是低频操作，可以接受）。

| `POST /api/coord/clear` | `name` | 撤销人工坐标，回到车站档案原值 |

## 时间条上的停站

时间条不只画进度，还把**每一停站的站名和时刻**直接标在轴上——轴上每隔一段就有一个小圆点，圆点下面两行小字，上行是站名、下行是时刻：

- **位置**按到站时刻在全程中的占比放（首站用发车时刻），所以站与站在轴上的疏密就是实际的运行快慢。
- **时刻口径**：首站显示发车，中间站显示到达，终到显示到达。悬停任一站点还能看到「到 / 开 / 停几分钟 / 完整日期时间」。
- **挤不下就错层**：站距太小、标签会打架时自动移到下一层，最多两层；首末站一定保留标签，实在挤就单独占第三层。
- **再挤不下只留圆点**：标签放不下的站仍然有一个小圆点在轴上（说明这站确实停了），悬停或点击就能看到时刻。
- **点标签 = 跳到那一刻**：列车图标和时间同时落到该站，播放暂停。
- 站多的时候时间条会变高，嫌挡地图就点右下角 **「停站」** 关掉，选择记在本机，下次打开还是关的。

> 站特别多的车（30 站以上）在 1000px 宽的窗口里一层只能放十来个标签，剩下的只能靠悬停。想全看到，把窗口拉宽或看左侧「车次详情」里的完整时刻表。

## 地图上的两种路线

车次详情的地图可以画两套走法，点车次详情里「按真实走向 / 回到站点直连」切换：

| | 怎么来的 | 适合看什么 |
|---|---|---|
| **站点直连**（默认） | `path_stations()` 把经由线路上的通过站也插进路径，站与站之间是直线 | 站序、里程、时刻：一眼看清在哪停、跑了多远 |
| **沿真实线路** | `GET /api/route/osm` → `railosm.build()`，用 `data/crtrain/geoms.json.gz` 的线路几何拼 | 线路实际怎么绕：弯道、绕行、跨江位置 |

**拼法**（`railosm.py`）：

1. 每个几何段（part）两端投到车次现有折线上，拿到里程和偏离，两端都贴着的段整段保留；
2. 段内按弧长线性插值出每点的里程 —— 不逐顶点筛，否则一段几何会被切成一堆碎渣；
3. 各段按里程区间贪心覆盖，复线上下行只留一条；
4. 覆盖不到的地方，用沿途通过站一站一站地直线补过去（比一根大斜线贴着线路得多），缺口位置和里程仍如实报给前端。

切到「沿真实线路」时，按钮右边会显示这次拼得怎么样，比如 `10 处缺口 · 94 km 走站间直线`；全程都贴合时显示 `全程沿真实线路`。

**实测数据**（2026-10-28，均取当天缓存）：

| 车次 | 区间 | 全程 | 折点数 | 缺口 | 缺口里程 | 覆盖率 |
|---|---|---|---|---|---|---|
| G1 | 北京南→上海虹桥 | 1302 km | 519 | 10 处 | 94 km | 93% |
| G1033 | 北京南→上海虹桥 | 1446 km | 429 | 0 | 0 | 100% |
| K8361 | 信阳→上海 | 792 km | 270 | 1 处 | 107 km | 86% |
| D1 | 北京西→长沙 | 1579 km | 824 | 1 处 | 216 km | 86% |
| D2290 | 深圳北→南通 | 1788 km | 669 | 3 处 | 660 km | 63% |

**已知局限**：这份几何是按线名切碎的（一条 1300 km 的高铁被切成 55 段，总长还是上下行双算的 2437 km）。所以：

- 干线车次贴合很好 —— G1 京沪 1302 km，只有 94 km 靠直线；
- 跨线 / 普速车次缺口多 —— D2290 深圳北→南通有 660 km 只能走站间直线（末段 600 km 那条线的几何还没进库）；
- 想让某条线本身画得准，从车次的经由线路名点进「车站 / 线路」页看那条线。
- 缺口只影响画得像不像，不影响里程、时刻和列车位置：位置一律按里程在折线上插值（`pointAtKm`），换哪套折线都对得上。

> **本项目只用「线路 + 车站」两类数据**：线路一侧是 `data/crtrain/lines.json` 的站序与里程，
> 车站一侧是 `stations.json` / `station_coords.json` 的坐标，走向靠 `geoms.json.gz` 里**按线名切好的**几何来对齐。
> 「把 OSM 全部铁路 way 建成一张路网再 A\* 寻路」那条路试过（早先的 `railgraph.py`），单程 6~11 秒、部分 OD 直接不连通，
> 还要背 300 MB+ 的 `railways.geojson`，和「按线名 + 走廊」比没有优势，**已从仓库移除，不再用这条路**。

## 关于「即时位置」

12306 不对外提供列车 GPS，所以位置由时刻表推算：

```
绝对时间 = 发车日期 00:00 + running_time（自始发站起的运行分钟）
段内位置 = 上游站坐标 + (下游站坐标 - 上游站坐标) × (已过时间 / 区间运行时间)
```

在区间内按匀速近似，停站时钉在站上。HUD 里的「速度」是区间平均速度（里程 ÷ 区间时长）。
优点是稳定、离线可用；缺点是列车晚点时会有偏差（见下方「后续」）。

## 已知限制

- **里程**分三档：`实测里程`（线路表匹配）/ `部分实测` / `里程估算`（直线 × 弯曲系数），页面上有角标。
- **坐标覆盖**：cnrail 库 7579 站全有坐标；12306 车站字典里另有约 0.7% 的老挝段、香港西九龙等缺失。
- 12306 接口有频控，短时间大量查询会 403；服务端有节流，仍建议不要连续狂点。
- 只能查「当天开行」的车次，非当日日期会查不到经停站。
