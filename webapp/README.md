# railcn webapp — 12306 车次查询 + 地图行程

把仓库根目录那套采集脚本整合成一个本地网页：输入车次就能看经停站、时刻表、线路走向，
并按时刻表推算列车此刻在地图上的位置。零第三方 Web 框架，只复用原有的 `trainclaw.py`。

```
railcn/
├─ config.py                  ← 原样复用（API 常量 / 字段索引 / 座位映射）
├─ trainclaw.py               ← 原样复用（TrainAPI 客户端 + 解析函数）
├─ collect_trains_p2.py       ← 原样复用（批量采集车次清单）
├─ collect_routes.py          ← 原样复用（批量采集经停站）
├─ cnrail_data_v2.xlsx        ← 车站 / 铁路线 / 站点-线路关联 原始底表
├─ data\                      ← 由上面那张表导出的 JSON（见「cnrail 数据层」）
```

## 快速开始

```bat
:: 方式一：双击
start.bat

:: 方式二：命令行
cd webapp
python server.py --port 8686 --open
```

打开 <http://127.0.0.1:8686/>。

## 功能

| 模块 | 说明 |
|---|---|
| 车次详情 | 输入 `G1` 回车 → 经停站时刻表（到/发/停留/里程）+ 地图线路 |
| 站站查询 | 输入起终站查实时余票（席别 / 票价 / 余票数），点一行直接看该车次行程 |
| 位置推算 | 按「运行时长」把时刻表换算成绝对时间，在相邻两站间按时间比例插值定位 |
| 时间轴 | 自绘时间条（不依赖原生 range，Chrome/Edge 一致），可拖拽/点击/方向键定位；跨日车次在时间条上按自然日分段并标零点刻度 |
| 地图 | 腾讯地图 GL JS（需自备 Key）；无 Key 时自动降级为无底图示意模式 |
| 车站 / 线路 | 查车站（路局 / 电报码 / 服务类型 / 连接线路）或线路（途经站点 + 累计里程），点线路名跳转；线路地图默认按 **OSM 真实走向** 画，可一键切回站点直连 |
| 数据下载 | 列出**含当日共 15 天**的日期，选一天批量下载当天**全部车次 + 经停站**，可暂停/续传/导出 JSON·CSV |
| 历史数据 | 已落库的全部日期（含下载窗口之外的更早日期）都能翻，按车次/始发/终到检索、点开看经停站、直接导出 |
| 跨日显示 | 车次详情区分第 1/2/3 日：头部行程带 + 跨零点分隔行 + 时刻旁 `+1`/`+2` 角标；HUD 与时间条均带日期 |
| 数据校对 | 扫全库车次标出「经由认不全 / 里程只能估算 / 缺坐标」，按问题筛选逐条补全；**每趟车的所有经停站都能改经纬度**（不只缺失的），两格都有粘贴拆分：`经度:126.576636,纬度:42.038926`、`126.576636,42.038926`、`126.576636E 42.038926N`、`126°34'35.9"E` 都认，顺序随意；手工值优先于自动结果，随改随生效 |

## 数据是怎么来的

1. **车次清单**：`collect_trains_p2.py` 用前缀搜索枚举全国 1.6 万趟车 → Excel
2. **经停站**：`collect_routes.py` 按 `train_no` 逐趟拉 → Excel（也可网页内实时按需拉）
3. **导入本地库**：`python tools/import_data.py`
4. **车站坐标**：12306 不提供经纬度，用 OSM 铁路站点数据匹配站名
   ```bat
   python tools/build_coords.py          :: OSM 导出 → station_coords.json（93%）
   python tools/fill_missing_coords.py   :: 残留缺失用 Overpass 补（98.6%）
   ```

> 网页查询优先读 SQLite 缓存；缓存未命中才向 12306 实时请求 1 次并写回。
> 所以第一批车次慢 1~2 秒，之后是本地毫秒级。

## cnrail 数据层（车站 / 线路 / 里程）

`cnrail_data_v2.xlsx` 补齐了 12306 完全不给的三样东西：车站档案、线路站序、**真实里程**。

```bat
python tools\xlsx_to_json.py        :: Excel → data\*.json（仓库根目录下）
```

| JSON | 内容 |
|---|---|
| `cnrail_stations.json` | 7579 站：中英文名、类型、行政区、经纬度、所属路局、电报码、服务类型、连接线路 |
| `cnrail_lines.json` | 417 条线：途经站点（有序）+ 每站累计里程 + 线路色 + `kmReliable` |
| `cnrail_index.json` | `{站名: [lat, lon]}`，前端/脚本直接取坐标 |
| `cnrail_meta.json` | 生成时间、坐标修正模型、覆盖率统计 |

**两个坑，脚本里都处理了：**

1. **坐标整体偏移**：原表经纬度是 `data = s × true + t` 的仿射变换结果
   （s≈1.016/1.012，t≈−5.12/+1.11），直接用会把北京南画到山西。
   用本地 OSM 车站坐标做稳健回归反解，残差中位 0.0005°（约 50 m）。
2. **站间距列不一定对齐站序**：部分线路的「站间距」个数少于站点数，按位置解析会错位。
   用「里程 ÷ 相邻站大圆距离」即弯曲系数校验，只保留 0.95~1.5 的线路（231/417）参与里程推算。

**里程怎么用**：把一趟车的相邻两站拿去线路表里查同线里程差，命中就用实测值；
未命中的区间按本趟已命中区间的弯曲系数（默认 ×1.12）折算。
结果在页面上标 `实测里程` / `部分实测` / `里程估算`，鼠标悬停可看匹配了哪几段。
G1 北京南→上海虹桥 因此从「直线 1176 km」修正为 **1318 km**（实际运营里程）。

**路径展开**：相邻两站若同处一条线，就把该线中间的站插进折线，
所以地图上是沿线的真实走向，而不是站与站之间的直线。列车位置也按里程在这条折线上取点。

## 按日期批量下载（数据下载页）

「数据下载」页签列出**含当日共 15 天**（今天 ~ 第 15 天），选中一天即可批量抓取当天全部车次与经停站。
窗口之外的历史数据不会丢：到「历史数据」页签照样能检索、查看、导出。

**为什么不是靠「12306 搜索接口枚举车次」**：那个接口限流极凶，几百次并发请求就会 403 封几十分钟。
这里利用一个更可靠的事实——**`train_no` 是车次的固定内部编号，跨日期不变**：

```
本地车次全集（17,222 条 code + train_no）   ← 来自历史采集，一次建好长期复用
        ↓ 对目标日期逐个查 queryTrainInfo
有经停站  → 说明当天开行：写 trains + routes 两张表
无经停站  → 说明当天不开行：写 day_skip 表，续传时不再重查
```

所以**只有第一次需要「刷新全集」**（走搜索接口，单线程 2 秒间隔，遇 403 自动冷却重试），
之后每天开跑都不碰那个接口。

| 机制 | 说明 |
|---|---|
| 断点续传 | 每批 40 条落库；随时可暂停，重启服务后点「继续」接着下 |
| 并发 | 1~8 线程可选，默认 6；单线程内每次请求间隔 0.45 秒 |
| 自适应退避 | 连续失败 5 次把间隔 ×1.35（上限 3 秒）；连续 25 次或遇到 403 自动暂停 |
| 全量保留 | 原始 JSON 存在 `rail.db` 的 `routes` 表，不清库、不过期；导出文件另存 `data/exports/` |
| 导出 | `railcn_<日期>.json`（完整结构）或 `railcn_<日期>_stops.csv`（停站明细，Excel 可直接打开） |

实测规模：一天约 **1.7 万趟候选**，实际开行 1.3~1.4 万趟，6 线程约 25~35 分钟跑完。

> 注意：`trains` 表里「已确认开行」只算拿到了经停站的车次；只被枚举进来但没验证的不计入。

### 一键连跑（刷新全集 → 按天依次下）

页面左上角「▶ 一键连跑」= 一条流水线，点一次就把整件事跑完：

```
刷新车次全集（12306 搜索接口，约 5~10 分钟，只在开始时做一次）
   ↓
第 1 天（今天）→ 第 2 天 → … → 第 15 天
```

- **队列按天串行**：上一天跑完才开下一天，不会同时抓多天（并发在单天内部，线程数照旧可选）。
- **重复点不重复跑**：已经下完的日子进去只剩 0 趟待处理，会瞬间跳过，所以每天点一次也不会浪费时间。
- **随时暂停**：「⏸ 暂停连跑」只停在当天，进度落库；再点「▶ 继续连跑」从这一天接着跑，
  **不会重刷全集**（除非中断发生在刷新全集那一步）。
- **进度看得见**：横幅显示「连跑中 3/15 · 第 3 天 10-28 周三 · 下载经停站 · 已跑 42 分钟」，
  列表里正在跑的那天可单独暂停，其余日子显示「排队中」。
- **断点跨重启**：连跑进度写进 `rail.db` 的 `chain_run` 表，服务重启后横幅变成「连跑已暂停」，
  点继续即可接上。
- **限流自保**：某天因 403/连续失败被自动暂停时，整条连跑一起停下并给出提示，不会空转。

#### 连跑是不是更容易被封？

单次请求速度没变，但连跑把「跑一天就停」拉成「连着跑几小时」，暴露窗口大了十几倍，
不加刹车确实更容易撞到 12306 的限流。所以加了三条：

| 刹车 | 行为 |
|---|---|
| 换天冷却 | 一天跑完停 60 秒再开下一天；上一天有失败、或刚被限流，冷却 180 秒 |
| 退避记忆不归零 | 被限流拉长的线程间隔（最高 3 秒）存进进程内的 `_THROTTLE`，**换天 / 继续**都继承；顺利时再慢慢降回 0.45 秒，半小时彻底没事才恢复原速 |
| 全集默认不刷 | 「刷新全集」要发 **800 个搜索请求**（81 个一位前缀 + 顶到单页上限的前缀再细分 10 个），是全流程最容易被 403 的一步。连跑只在「本地全集不足 1000 趟」或「一周没刷过」时才刷；其余情况直接跳过，并在横幅写明原因。要强制刷仍可在某天详情点「刷新全集」 |
| 只细分必要的词 | 搜索接口单页上限 200，只有返回 ≥195 条的前缀才继续细分，避免为没顶到上限的词白跑请求 |

> 一句实话：枚举这一步的请求量砍不掉（一位前缀几乎全都顶到 200 条，必须细分），
> 能改的是**别每次都做**。数据下载真正的主力是「按 train_no 查经停站」，那个接口宽容得多。

页面上的「并发线程」照样是最终速度旋钮：2 线程最稳，6 线程最快。

> 顺带修掉一个老口径问题：`universe()` 与「待处理」统计原来各取一行的 `train_no`
> （同一车次号在不同日期可能登记了不同编号），导致页面显示待处理 2377 实际只跑 218。
> 现在两处统一取 `MAX(train_no)`，待处理数与真正要跑的趟数一致。

## 经由推断与人工校对

### 自动推断：三档证据，强的先说话

`cnrail.infer_via()` 逐对相邻站判断「这一段走哪条线」，按可信度取最强者：

| 档 | 依据 | 说明 |
|---|---|---|
| `km` | 线路里程表 | 两站同线且站序正确、里程差合理 —— 最可靠，通常说明该段确在此线上 |
| `pos` | 线路站序 | 两站都出现在该线站序里且前站在前，不要求相邻（跳站车次也能认） |
| `lines` | 车站档案 | 两站「连接线路」的交集 —— 最弱，只作兜底 |

同一档里优先选**与上一段连续**的线路（`京广高速线` 与 `京广线` 视为同族），
避免在两三条并行线之间来回跳。输出是**结构化区间**而不是线路名列表：

```json
[{"line":"峰福线","from":"福州","to":"武夷山","i0":0},
 {"line":"京九线","from":"南昌","to":"商丘","i0":6}]
```

区间之间若有一对站认不出，会单独给出 `unknown: [{"from":"武夷山","to":"南昌","i0":4}]`，
界面上就落在链路的正确位置（而不是全部堆到末尾），编辑行里也直接变成「线路名待填」的空行。

> 为什么必须做这一步：很多车次在里程表里一段都匹配不上（`郑州`、`洛阳` 这类枢纽站
> 恰好不在「里程可信」线路的站序索引里，全库 7579 个站只有 2426 个有站序），
> 光靠里程算经由会得到空结果。补上后两档后，K3、T197、Z21 这类车次都能认出主要经由。

### 人工校正：存下来，优先用

| 表 | 内容 |
|---|---|
| `train_override` | `code`（主键，按车次不按日期）、`via_json`、`total_km`、`seg_km_json`、`note`、`updated_at` |
| `coord_override` | `name`、`lat`、`lon` —— 车站坐标人工修正（**任何站都能改**，不限于缺坐标的） |
| `line_override` | `name`（主键，线路名）、`seg_km_json`、`total_km`、`note`、`updated_at` —— 线路里程人工校正 |
| `line_custom` | `name`、`stations_json`、`note` —— 用户新增的线路（档案里没有的） |
| `station_custom` | `name`、`lat`、`lon`、`lines_json`、`tele`、`bureau`、`note`、`type`（车站/线路所）、`source`（manual 自建 / line-fill 线路补全）、`alias`（线路里的原写法）、`coord_src`（osm/manual）—— 用户新增 + 线路补全的车站 |
| `curate` | 全量扫描结果：每趟车的经由 / 里程 / 缺坐标摘要与问题标签 |

`build_route_payload()` 里自动结果算完后再套人工值：

- 有 `via_json` → `viaLines` / `viaSegs` 整体替换，`viaSource=manual`，不再显示缺口
- 有 `total_km` → 各站里程按 `total_km / 自动末站里程` 等比缩放，`kmMode=manual`
- 有 `seg_km_json` → **逐段锁死**：`{"0":205,"2":230}` 表示「第 1 段（第 1 站→第 2 站）205 km」、
  「第 3 段 230 km」；手填段用填的值，其余段沿用自动值，从 0 开始重新累加各站累计里程。
  若同时又填了 `total_km`，则只把**没手填的那些段**按比例缩放到 `total_km − 手填段之和`，
  这样既能锁定已知的精确区间，又能保住全程总量

`seg_km_json` 的键是「区间序号」而不是站名，因为区间序号在同一趟车的上下行、不同日期里都稳定，
站名偶尔会因经停变化（加开 / 甩站）而错位。

### 线路里程人工校正

线路的里程来自 `cnrail_lines.json`（417 条线，其中 182 条有站缺里程、2 条没有总里程）。
「车站 / 线路」页选中线路后点「编辑里程」，改的是**这条线本身**：

- 相邻两站逐段列出，灰字是档案值，档案缺的段显示 `-`（不详），留空即沿用
- 填了就锁住该段；底部的「线路总里程」同样可改，填了就把**没手填的段**缩放到「总里程 − 手填段之和」
- 保存进 `line_override`；「全部恢复档案」删掉这条记录

生效方式和车次里程不同：`railcore` 启动时把 `line_override` 灌进 `cnrail`，
`cnrail.rebuild_lines()` 用人工值重算各站累计里程并**重建「站名 → 线路里程」索引**，
所以之后车次里程配对（`refine_km` / `_pair_km_raw`）用的就是改过的数；缺口的段保持 `None`，
不会外推（界面上仍是 `-`）。人工改过的线路即使档案标着「里程不完整」也会进索引 ——
否则改完不生效，等于白填。

生效是**即时**的：payload 每次请求现算，不缓存最终结果，改完刷新详情页就是新数据。
`GET /api/curate/detail` 特地带 `use_override=False` 跑一遍，专门给编辑器显示「自动推断基线」，
改错了还能对照原来是什么。

### 车站表补全（线路里有、站表里没有）

车站档案只有 7579 条，线路 / 资料库里却出现过 1860 个档案没有的站名
（大量地方小站、线路所，档案只收了大站）。`scripts/fill_missing_stations.py` 把这些补进
`station_custom`（`source='line-fill'`），站表随之从 7579 → 9443：

```
python scripts/fill_missing_stations.py                 # 只统计
python scripts/fill_missing_stations.py --apply         # 写库（--report docs/station-fill.json 出清单）
```

- 站名来源三处：`data/cnrail_lines.json`、`line_custom`、`line_catalog_stop`（辉睿线路资料库）
- 站名按档案口径截掉尾部「站」（`上虞站` → `上虞`），原写法记在 `alias`；
  「十八站」这类地名自带的「站」不动。`线路所 / XX所` 是独立设施，**不能被 `cnrail._key` 截成 `XX`**，
  所以这类站的合并键用全名，免得把同名车站顶掉
- 坐标能对上 OSM 派生库（`station_coords.json`）的就直接填（883 个），对不上的留空，
  之后在车站详情里用「补坐标」框一行行补
- 补进来的站在详情里带「线路补全」标记，站名联想（`/api/stations`）也能搜到

### 线路真实走向（OSM · CRTrainRoute）

线路库里只有「站序 + 里程」，没有轨道走向，地图上一直是站点直连。接入
[Laide140/CRTrainRoute](https://github.com/Laide140/CRTrainRoute)（MIT）的 OSM 数据后，
每条线都能按真实轨道画：

```bat
python scripts\fetch_crtrain.py      :: 拉 32 个省级 geojson（约 142 MB）+ 站名/坐标
python scripts\import_crtrain.py     :: 归集成 data\crtrain\lines.json + geoms.json.gz
```

- 数据来源：CRTrainRoute 仓库 `data/geojson/*.geojson`（底层是 OSM 铁路线，要素带 `name` = 线路名），
  一共 **3007 条线、17.4 万个铁路要素、16.0 万 km**（上下行去重后）
- **里程怎么算的**：按线名归集后把节点量化到 1e-4°（约 11 m）建图——上下行两条平行轨在这个精度下并成一条，
  所以不会出现「京沪线 2994 km」这种翻倍；再对每个连通段取直径（两次 Dijkstra）相加。
  京沪线 1434 km（档案 1463）、京沪高铁 1296（实 1318）、陇海 1696（实 1750），误差都在 2% 内
- **几何怎么存的**：OSM 一条线被切成几千个 2~3 点的 way，先按端点相连 + 转向 < 90° 接成长折线
  （京沪线 2170 段 → 102 节），再 Douglas-Peucker 抽稀到 25 m，坐标留 5 位小数。
  落盘 `geoms.json.gz` 只有 1.4 MB
- **怎么对上线路名**：精确 → 同族（去掉 `线 / 铁路 / 高速线 / 高铁 / 客专线 …` 后的主干名）。
  同族里可能有 `京沪高铁`（1296 km）和 `京沪高速铁路`（9 km 残段）两个，取里程最长的；
  口径必须一致——客运专线不套普速线（`包西高速线` ≠ `包西铁路`）；给了已知里程时，
  几何里程不到它 35% 的残段直接排除（`潍烟高速铁路` 只剩 2 km，对不上 585 km 的潍烟高铁）。
  档案 417 条里 325 条能对上，线路资料库 844 条里 532 条能对上
- **界面**：线路详情多一张「真实走向」卡（OSM 线名 / 几何里程 / 连通段 / 桥隧数 / 与档案里程差），
  带「改站点直连 ↔ 按真实走向」开关（`localStorage['railcn.lineGeom']`）；
  线路库里查不到的线，会先翻资料库、再翻这 3007 条 OSM 线，点开就能看走向

> 坐标系：OSM 是 WGS-84，前端统一转 GCJ-02 再画；12306 车站坐标本身是 GCJ-02，不参与这个换算。

### 新增线路 / 车站

档案只有 417 条线、7579 个站，总会有缺的（新建线路、地方小站、专用线）。

- **新增线路**：填线路名 + 沿线站序，每站可选填「自起点累计公里数」，不详就留空（存成 `null`，界面仍是 `-`）。
  校验：至少两站、站序不重复、累计里程必须严格递增、不能与档案线路重名
- **新增车站**：填站名 + 经纬度（可直接粘贴「经度,纬度」或「经度:126.576636,纬度:42.038926」，
  复用校对页的拆分规则），可选填所属线路 / 电报码 / 路局。
  已在站库里的站会被拒绝，避免与 `coord_override` 两套坐标打架
- **补坐标**：车站详情里有个「补坐标」框，粘一行就能存（`POST /api/coord` 的 `coord` 字段），
  存完立刻重算相关车次，坐标值后面标「（人工）」
- 自建的条目在详情里带「自建」标记，删除按钮点两下才生效（第二次确认）

落库后走 `railcore._apply_custom()` → `cnrail.set_custom(lines, stations)`：

- 自定义线路插在 `_LINES` 最前面，同名档案线路被覆盖（保存时已禁止重名，这里只是保险）
- `rebuild_lines()` 会把它们一并算进 `_POS`，所以**新增的线路立刻能用于车次经由 / 里程推断**
- 自定义车站合并进 `_STATIONS`（已有的站只补空字段：坐标 / 电报码 / 路局 / 线路），
  再 `stations.reload_coords()` 让坐标缓存重新读，新站马上能在地图上画出来

新增线路的里程若还想改，照旧用「编辑里程」，覆盖值存在 `line_override`，与自定义线路的数据分开；
删除自定义线路时会连带清掉它的 `line_override`，免得以后重建同名线路套到旧值。

### 地图：经由线路上的全部车站

`cnrail.path_stations(stops, prefer=经由线路名)` 把经停站序列展开成「线路上全部车站」：

- 相邻两站在同一条线上时，把该线中间的站补进来；里程按 `本趟车两站里程 / 该线两站里程` 的比例映射
- `prefer` 是推断（或人工校正）出来的经由线路名，命中时优先按它展开，其次才按里程比匹配
- 输出 `[{name, lat, lon, km, stop, idx}]`，`stop=False` 表示列车通过但不办客；线路所 / 中继站直接丢弃
- `path`（画线用的折线）与 `lineStops`（打点用的车站）来自同一次展开，保证点位与折线严丝合缝

前端两种地图后端都按这个画：实心蓝点＝停车站，旁边标「站名 + 发车时刻」（终到站标到达时刻）；
浅灰小点＝通过站（不标字，标了会糊成一片），点一下看里程与所属车次。

### 校对页

左列按问题筛选（待补全 / 经由全无 / 经由缺口 / 里程 / 缺坐标 / 已校正 / 无问题 / 全部），
右侧编辑器做四件事：

1. **分段填经由** —— 线路名是下拉选择（`▾` 展开全部 417 条，打字即时过滤，`↑↓` 移动、`Enter` 选中、
   `Esc` 关闭；库里没有的名字照填照存，会作为最后一项「用这个名称」出现），站名按该车经停表补全
2. **站间里程逐段改** —— 按相邻两站列出全部区间，灰字是自动值、留空即沿用，填了就锁住这一段；
   行尾显示与自动值的差（`+9.0` / `-5.0` / `=`），改了哪段一眼看得见，`↺` 单段还原、
   「全部恢复自动」整列还原；底部的合计、以及「经停站与里程」里的各站累计值都随输入实时重算
3. **总里程** —— 可留空；填了就对「没手填的段」做等比缩放
4. **改任意车站的经纬度** + 写备注

保存前会校验：

- 每段必须有线路名
- 区间首尾相接（「第 N 段到 X，第 N+1 段却从 Y 起」会直接指出来）
- 站名必须在这趟车的经停站里
- 总里程与自动值差 25% 以上时提示确认
- 手填的站间里程与自动值差 3 倍以上时提示核对（只提示，不拦保存）

全量扫描约 11800 趟、4 分钟（约 20 ms/趟）。扫描时**先算后写**、攒 40 条一个短事务落盘，
否则一边算一边挂着写锁，用户点保存会被锁到超时。

### 车站坐标编辑

「车站坐标」卡片列出该车**全部**经停站，不是只列缺坐标的——档案里的坐标本身也可能错
（同名站串号、老数据偏移），能改才有意义。每行显示：序号 + 站名、纬度、经度、
来源徽标（`档案` / `人工` / `缺失`）、保存、还原。

- 经纬度按 **WGS-84** 填（与 OSM 一致），前端再换算成腾讯地图用的 GCJ-02，不用自己转
- 支持**成对粘贴**：把 `115.67135293489208,37.32526706163806` 粘进任一格（经度在前、纬度在后），
  自动拆成两格；中文逗号 / 分号 / 空格分隔都认，`纬度,经度` 反着写也能靠取值范围自动纠正
- 保存写 `coord_override`，**立即失效坐标缓存**并重算引用该站的车次；
  地图定位、线路走向、里程插值下一次请求就是新值
- `还原` 删掉人工值，回到车站档案原值；档案里也没有就退回「缺失」
- 卡片支持按站名筛选、勾选「只看缺坐标」，缺失行用红底标出
- 保存只重画当前行，不会冲掉你在别处正在编辑的经由；切回车次详情时会静默重拉一次

> 撤销坐标有个坑：`refresh_station()` 原本靠 `curate.missing_json LIKE '%站名%'` 找受影响车次，
> 撤销后该站已不在缺失清单里，一行都匹配不到、清单上的缺坐标数不会回退。
> 现在匹配不到时回退到 `routes.raw LIKE '%"station_name": "站名"%'` 反查
> （全表扫描约 0.3 s，撤销是低频操作，可以接受）。

## 关于「即时位置」

12306 不对外提供列车 GPS，所以位置由时刻表推算：

```
绝对时间 = 发车日期 00:00 + running_time（自始发站起的运行分钟）
段内位置 = 上游站坐标 + (下游站坐标 - 上游站坐标) × (已过时间 / 区间运行时间)
```

在区间内按匀速近似，停站时钉在站上。HUD 里的「速度」是区间平均速度（里程 ÷ 区间时长）。
优点是稳定、离线可用；缺点是列车晚点时会有偏差（见下方「后续」）。

## 已知限制

- **里程**分三档：`实测里程`（线路表匹配）/ `部分实测` / `里程估算`（直线 × 弯曲系数），页面上有角标。
- **坐标覆盖**：cnrail 库 7579 站全有坐标；12306 车站字典里另有约 0.7% 的老挝段、香港西九龙等缺失。
- 12306 接口有频控，短时间大量查询会 403；服务端有节流，仍建议不要连续狂点。
- 只能查「当天开行」的车次，非当日日期会查不到经停站。
